# Reviewed policy changes and revisions

Policy export uses schema version 2. Import accepts version 2 and legacy files with no version (version 1). Unsupported versions, unknown keys, duplicate YAML keys, reused collection aliases, invalid conditions, missing models or fields, and missing or ambiguous references stop validation. A failed import leaves the entire file unapplied.

## Import workflow

1. Upload a policy file and select **Validate and Preview**.
2. Read the current/proposed configuration comparison. Validation does not activate or modify profiles.
3. Confirm changes to active profiles when the current or proposed profile is active.
4. Select **Apply Reviewed Import**. The server checks that both the uploaded file and every affected policy still match the preview. A changed rule line also invalidates the preview.

Uploading another file clears the review evidence and active-profile confirmation. Review evidence is generated by the server and cannot be supplied or edited through RPC.

A missing key preserves an existing value. An explicit `null` clears an optional scalar or collection; `[]` clears a collection. Boolean values must be YAML `true`, `false` or `null`, not strings. A profile name is required. Each child-rule collection present in the file replaces that collection completely.

Users, companies, menus, reports and server actions are exported with external IDs when available. Users have a login fallback; companies and menus have a name/path fallback; custom actions include model and, for reports, report name. An external ID takes precedence. When it is unavailable on the destination, the fallback must resolve to exactly one record. Missing or ambiguous fallbacks stop the import instead of weakening the policy silently. Profiles resolve by external ID, then unique name.

## Revision behavior

Validated imports, restores and changes made through the shared reviewed-apply service save immutable before/after snapshots. New profiles receive an after snapshot. Snapshots capture enforcement settings and direct profile user assignments; they do not copy role approvals or assignment lifecycle records.

Ordinary profile and rule-form edits are not automatically versioned. Select **Save Revision** before editing to preserve a restore point. **Revisions** shows that profile's saved snapshots. This distinction is intentional and should be included in administrator training.

All policy/profile and child-rule mutations share a transaction lock with role governance, then lock affected profile rows in ID order. A parent row version fence makes concurrent rule insertions visible as serialization conflicts even under Odoo's repeatable-read transaction isolation. Reviewed operations reject stale policy fingerprints after the framework retries a conflicting transaction.

Restoring a revision opens a comparison first. The server checks the snapshot hash and current-policy fingerprint, locks the profile and rule rows, and rejects stale previews. Restores keep the current profile identity/name and save the preceding state as another revision. A deleted profile cannot be restored through its old revision; export/review the policy as a new import instead.

Revision records cannot be created, edited or deleted through ordinary model RPC. Snapshot creation and restore helpers check Access Studio Manager permission. Database administrators retain direct database control; these records are application-level audit evidence, not tamper-proof external storage.

## Internal integration API

These underscore-prefixed methods are private server APIs, unavailable over ordinary RPC. Call them under the original manager's environment; do not add a user-controlled context bypass.

```python
Revision = env['eh.access.revision']
Wizard = env['eh.access.yaml.wizard']

fingerprint = Revision._policy_fingerprint(profile)
revision = Revision._snapshot(profile, 'Manual review baseline')

# Resolve references and validate syntax without changing live policies.
existing, values = Wizard._prepare_entry(portable_policy)

# Atomic application after a caller has shown its own review and approval UI.
profile = Wizard._apply_entry(
    portable_policy,
    expected_fingerprint=fingerprint,
    confirm_active=True,
    reason='Approved policy draft',
)

# Restore only after review of the current policy and selected snapshot.
revision._restore(expected_fingerprint=fingerprint, confirm_active=True)
```

For a new profile, the expected fingerprint is SHA-256 of the canonical empty JSON object (`{}`). Existing-policy fingerprints include child rules, direct assignments and all supported restriction flags. Integrations should regenerate their preview when fingerprints differ; never retry with a freshly fetched fingerprint without another review.

Profile snapshots contain the materialized profile membership links. They do not
restore role assignment ownership or approval history. Current governed assignments
are reconciled during policy changes; review the resulting membership alongside
Roles and Assignments when restoring an older profile snapshot.
