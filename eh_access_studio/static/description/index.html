Two tools that work together

Profiles narrow access and shape the interface. Roles assign native Odoo groups and restriction profiles to users, with an accountable assignment history.

Native groups can grant access. A restriction profile cannot grant what native Odoo permissions deny. Role company scope governs administration and recipient eligibility; it does not make native group membership company-local. Native record rules and company rules still matter.

Included workflows

From a policy idea to a reviewed assignment

1. Build a guided policy draft

Choose a starter template and an installed model. Discover named buttons, tabs, links, and search controls from actual views. Build record filters with owner or hierarchy scopes and a visual condition editor. Templates and guided additions use inactive profiles so you can review them before activation.

Hierarchy scopes need HR employee relationships. Calendar presets target Date fields; other conditions remain available in the visual editor. Existing live restrictions can stay active while you prepare a separate draft.

2. Inspect current access

Select a user, model, operation, company, and optional record. Inspect native Odoo access alongside Studio restrictions, with contributing groups, rules, profiles, and record filters shown in the result.

The inspector reports allowed, denied, conditional, or unknown. It does not execute business create, write, or delete operations. It cannot guarantee a custom workflow or an operation using proposed values will succeed.

3. Assign roles with a reason and a lifecycle

Bundle native groups, included roles, and company-scoped profiles. Record who receives the role, why, and when the assignment starts and ends. Track owned memberships so revocation preserves overlapping assignments and independently held access.

Reconciliation is scheduled every minute. Start and expiry enforcement depend on a healthy scheduler. Expiring a restriction profile removes a restriction; use an expiring role assignment when you intend to remove a grant.

4. Handle employee access requests

Internal employees can request eligible roles with a reason and end time, and follow their own requests. Another manager reviews the request before an assignment is created. The manager Overview highlights pending requests, upcoming expiry, overdue reconciliation, and recent governance events.

Request ownership, company scope, and manager privileges are checked on the server. Managers cannot approve their own requests. Dashboard counts support follow-up; they are not a risk score.

5. Review imports and keep policy revisions

Preview YAML policy differences before import. References are validated, changes after preview are detected, and active-policy changes require explicit confirmation. Save an immutable policy revision and restore a selected revision with a review step.

Imports, restores, and AI-created policies create snapshots automatically. Ordinary form edits require Save Revision. Governance evidence records managed actions; it is not a log of every read or denied operation, and application immutability does not prevent database-administrator changes.

6. Generate an optional AI policy draft

Describe restrictions for one selected business model. With your explicit consent, the configured OpenAI provider receives your prompt and that model's selected field schema. Review the structured response, then create an inactive profile in a separate step.

No business record values, user list, or existing policy contents are automatically included. AI does not activate the profile, assign users, or generate role grants. Review global switches and all generated conditions. Provider handling is covered by mocked tests; live-provider validation is not claimed.

Know what each control does

A hidden control and a denied operation serve different purposes. Configure the server restriction when an operation must be blocked, then use interface controls to make the available workflow clear.

ControlBehavior and scope
Model operations and record filtersStudio hooks check covered ORM operations alongside native Odoo access. Filters use current user, company, date, and hierarchy context. Test the installed application's actual workflow, including any custom code.
Field restrictionsVisibility, read-only, and required rules cover the module's supported view and server paths. Hidden-field handling is not encryption or a universal guarantee against custom computations and third-party endpoints.
Menus, tabs, and named controlsThese shape the interface. Hiding a named business button does not generally disable its underlying method. Use model restrictions or application-specific authorization for the operation itself.
Roles and assignmentsThese can add native group membership and profile membership. Privileged group grants are restricted. Native groups remain database-wide, even when the role is administered for one company.
Privileged executionCode running with elevated rights can bypass ordinary user access restrictions. Review custom modules and integrations that use elevated execution.

Profile composition matters: applicable record domains can combine permissively. Review all profiles affecting the user, including assignments from multiple roles, and inspect the resulting access.

Practical setup

What do I need?

The matching Odoo 19 Community package, the standard base, mail, and web modules, and the PyYAML Python dependency. HR employee relationships are needed for the guided team and subordinate scopes. The AI feature is optional and needs a system administrator to configure OpenAI.

How should I introduce a policy?

Start with an inactive draft. Review company scope, native groups, and overlapping profiles. Save a revision, activate the reviewed policy, inspect a representative user and record, and exercise the real workflow in a test environment. The profile's Manual Test Instructions button provides manual test guidance.

What validation is included?

The module includes a test suite for access enforcement, configuration validation, governance, revisions, guided workflows, and optional AI handling. Test results apply to the package and runtime tested; they are not a certification of custom modules or deployments.

Is it free?

Yes. The module is free under LGPL-3, with no paid feature tier. Hosting, implementation services, and any optional AI provider charges are separate. The included HOWTO explains setup and operational limits.
